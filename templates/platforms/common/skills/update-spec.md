# 更新代码规范——沉淀可执行契约

当你学到有价值的东西（来自调试、实现或讨论），用本 skill 更新相关的代码规范文档。

**时机**：完成任务、修好 Bug 或发现新模式之后

---

## 代码规范优先规则（关键）

在本项目中，实现工作的“规范”指**代码规范**：
- 可执行的契约（不只是原则性文字）
- 具体的签名、负载字段、环境变量键与边界行为
- 可测试的验证/错误行为

如果改动涉及基础设施或跨层契约，代码规范的深度是强制的。

### 强制触发条件

改动包含以下任一项时，采用代码规范深度：

- 新增/变更命令或 API 签名
- 跨层请求/响应契约变更
- 数据库模式/迁移变更
- 基础设施集成（存储、队列、缓存、密钥、环境变量接线）

### 强制产出（7 节）

触发的任务需包含以下全部章节：
1. 范围 / 触发条件
2. 签名（命令/API/数据库）
3. 契约（请求/响应/环境变量）
4. 验证与错误矩阵
5. 好/基准/坏案例
6. 需要的测试（附断言点）
7. 错误与正确对照（至少一对）

## 何时更新代码规范

| 触发条件 | 示例 | 目标规范 |
|---------|----------|----------|
| **实现了一个功能** | 新增集成或模块 | 相关规范文件 |
| **做了设计决策** | 在可扩展性与简洁性之间选了前者 | 相关规范 + “设计决策”一节 |
| **修了一个 Bug** | 发现错误处理中的微妙问题 | 相关规范（例如错误处理文档） |
| **发现了一个模式** | 找到更好的代码组织方式 | 相关规范文件 |
| **踩了一个坑** | 学到 X 必须在 Y 之前做 | 相关规范 + “常见错误”一节 |
| **确立了一个约定** | 团队就命名模式达成一致 | 质量指南 |
| **新的思考触发点** | “做 Y 之前别忘了检查 X” | `guides/*.md`（作为检查清单项） |

**关键洞察**：代码规范更新不只是为了记录问题。每一次功能实现都包含设计决策与契约，未来的 AI/开发者需要它们才能安全执行。

## 规范结构总览

```
.sunshine/spec/
├── <layer>/           # 每层的编码标准（例如 backend/、frontend/、api/）
│   ├── index.md       # 总览与链接
│   └── *.md           # 主题指南
└── guides/            # 思考检查清单（不是编码规范！）
    ├── index.md       # 指南索引
    └── *.md           # 主题指南
```

### 关键：代码规范与指南——分清区别

| 类型 | 位置 | 用途 | 内容风格 |
|------|----------|----------|----------|
| **代码规范** | `<layer>/*.md` | 告诉 AI“如何安全实现” | 签名、契约、矩阵、案例、测试点 |
| **指南** | `guides/*.md` | 帮助 AI“实现前思考什么” | 检查清单、问题、指向规范的链接 |

**判断规则**：问自己：

- “这是**怎么写**代码”→ 放在规范层目录
- “这是**写之前要考虑什么**”→ 放在 `guides/`

**示例**：

| 学到的东西 | 错误位置 | 正确位置 |
|----------|----------|----------|
| “这项任务用 API X 而不是 API Y” | ❌ `guides/`（对思考指南来说太具体） | ✅ 相关规范文件（具体约定） |
| “做 Y 时记得检查 X” | ❌ 规范文件（对规范来说太抽象） | ✅ `guides/`（思考检查清单） |

**指南应该是简短的、指向规范的检查清单**，而不是重复详细规则。

## 更新流程

### 步骤 1：明确你学到了什么

回答这几个问题：

1. **你学到了什么？**（具体说明）
2. **为什么重要？**（它防止了什么问题？）
3. **它属于哪里？**（哪个规范文件？）

### 步骤 2：给更新分类

| 类型 | 描述 | 做法 |
|------|----------|----------|
| **设计决策** | 为什么选方案 X 而不是 Y | 加入“设计决策”一节 |
| **项目约定** | 本项目如何做 X | 加入相关章节并附示例 |
| **新模式** | 发现的可复用做法 | 加入“模式”一节 |
| **禁用模式** | 会引发问题的写法 | 加入“反模式”或“不要”一节 |
| **常见错误** | 容易犯的错误 | 加入“常见错误”一节 |
| **约定** | 已达成一致的标准 | 加入相关章节 |
| **坑** | 不明显的现象 | 加警告提示 |

### 步骤 3：阅读目标代码规范

修改前，先读当前代码规范，以：
- 了解现有结构
- 避免重复内容
- 找到合适的章节

```bash
cat .sunshine/spec/<category>/<file>.md
```

### 步骤 4：执行更新

遵循以下原则：

1. **具体**：给出具体示例，不只抽象规则
2. **讲清原因**：说明它防止了什么问题
3. **展示契约**：加入签名、负载字段与错误行为
4. **展示代码**：为关键模式加入代码片段
5. **保持简短**：每节只讲一个概念

### 步骤 5：更新索引（如需要）

如果你新增了章节，或代码规范的状态发生了变化，更新该分类的 `index.md`。

如果目标规范文件头上有 `## 索引` 一节，同步更新索引表（新增、改动、删除的内容要在索引里体现）；索引是导航不是替代，拿不准就读正文。

更新完正文后，跑一遍 `sunshine spec index` 让命令按标题自动对齐索引（新增的节进索引、删掉的节出索引、旧描述保留），不用手改索引表：

```bash
sunshine spec index
```

## 更新模板

### 基础设施/跨层工作的强制模板

```markdown
## 场景：<名称>

### 1. 范围 / 触发条件
- 触发条件：<为什么需要代码规范深度>

### 2. 签名
- 后端命令/API/数据库签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境变量键（必填/可选）

### 4. 验证与错误矩阵
- <条件> -> <错误>

### 5. 好/基准/坏案例
- 好：...
- 基准：...
- 坏：...

### 6. 需要的测试
- 单元/集成/端到端测试及断言点

### 7. 错误与正确对照
#### 错误
...
#### 正确
...
```

### 补充一条设计决策

```markdown
### 设计决策：[决策名]

**背景**：要解决什么问题？

**考虑过的选项**：
1. 选项 A - 简述
2. 选项 B - 简述

**决策**：我们选了选项 X，因为……

**示例**：
\`\`\`typescript
// 如何实现
code example
\`\`\`

**可扩展性**：未来如何扩展……
```

### 补充一条项目约定

```markdown
### 约定：[约定名]

**内容**：约定的简述。

**原因**：本项目为什么这么做。

**示例**：
\`\`\`typescript
// 如何遵守该约定
code example
\`\`\`

**相关**：相关约定的链接。
```

### 补充一个新模式

```markdown
### 模式名

**问题**：解决什么问题？

**方案**：做法简述。

**示例**：
\`\`\`
// 好
code example

// 坏
code example
\`\`\`

**原因**：为什么这样更好。
```

### 补充一个禁用模式

```markdown
### 不要：模式名

**问题**：
\`\`\`
// 不要这样写
bad code example
\`\`\`

**为什么不好**：问题说明。

**应该这样**：
\`\`\`
// 应该这样写
good code example
\`\`\`
```

### 补充一个常见错误

```markdown
### 常见错误：描述

**症状**：出了什么问题

**原因**：为什么会发生

**修复**：如何纠正

**预防**：如何避免再次发生
```

### 补充一个坑

```markdown
> **警告**：不明显行为的简述。
>
> 何时发生、如何处理的细节。
```

## 交互模式

如果你不确定要更新什么，回答以下提示：

1. **你刚完成什么？**
   - [ ] 修了一个 Bug
   - [ ] 实现了一个功能
   - [ ] 重构了代码
   - [ ] 讨论了方案

2. **你学到或决定了什么？**
   - 设计决策（为什么选 X 而不是 Y）
   - 项目约定（本项目如何做 X）
   - 不明显的行为（坑）
   - 更好的做法（模式）

3. **未来的 AI/开发者需要知道吗？**
   - 为了理解代码如何工作 → 需要，更新规范
   - 为了维护或扩展功能 → 需要，更新规范
   - 为了避免重复犯错 → 需要，更新规范
   - 纯粹一次性的实现细节 → 可以跳过

4. **它与哪个领域相关？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织/复用
   - [ ] 质量/测试

## 质量检查清单

完成代码规范更新之前：

- [ ] 内容是否具体、可执行？
- [ ] 是否包含代码示例？
- [ ] 是否讲清了原因，而不只是内容？
- [ ] 是否包含可执行的签名/契约？
- [ ] 是否包含验证与错误矩阵？
- [ ] 是否包含好/基准/坏案例？
- [ ] 是否包含带断言点的必要测试？
- [ ] 是否在正确的代码规范文件中？
- [ ] 是否与已有内容重复？
- [ ] 新团队成员能否看懂？

## 与其他命令的关系

```
开发流程：
  学到东西 → {{CMD_REF:update-spec}} → 知识已沉淀
       ↑                                  ↓
  {{CMD_REF:break-loop}} ←──────────────────── 未来会话受益
  （深度 Bug 分析）
```

- `{{CMD_REF:break-loop}}`——深度分析 Bug，常常揭示需要更新的规范
- `{{CMD_REF:update-spec}}`——真正执行更新
- `{{CMD_REF:finish-work}}`——提醒你检查规范是否需要更新

## 核心理念

> **代码规范是活文档。每一次调试、每一个“原来如此”的瞬间，都是让实现契约更清晰的机会。**

目标是**制度记忆**：
- 一个人学到的东西，所有人受益
- AI 在一个会话学到的东西，沉淀到未来会话
- 错误变成有记录的护栏
