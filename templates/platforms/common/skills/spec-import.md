# 把现成文档整理成规范——带索引的 spec

把用户已有的文档（设计稿、接口文档、README、导出的 wiki、会议纪要等）整理成 Sunshine 的规范文件，落到 `.sunshine/spec/`，并配好文件头上的 `## 索引` 一节。

**时机**：用户说“我有一份现成的文档，帮我整理成 spec”时；接手一个已有文档的项目、第一次跑 `sunshine init` 之后。

---

## 先分清：这是整理，不是重写

- **整理**：把已有的内容按 spec 的格式重新组织——分到对的文件、配上索引、补上缺的标题。意思不改，不发明、不删减。
- **不是重写**：不要凭空补你不知道的东西。文档里没写的接口、没定的字段，不要编；缺失的部分列出来请用户补，不要自己猜。
- **不是 bootstrap**：`sunshine-spec-bootstrap` 是从代码库分析起 spec；本 skill 是从现成文档起 spec。输入不同，输出一样（`.sunshine/spec/` 下带索引的规范文件）。

---

## 步骤 1：先读，再动手

1. 问用户要整理的文档是哪些（文件路径、链接、或直接贴进来）。
2. 全部读一遍，先弄清：这份文档讲的是整体架构、前端、后端，还是混在一起？
3. 看一眼当前的 `.sunshine/spec/` 里已经有什么，避免重复写、避免覆盖已填的内容。`init` 只写不存在的文件，绝不覆盖已填内容；本 skill 也一样。

## 步骤 2：分到对的文件

| 文档内容讲的是 | 写到 |
|---|---|
| 整体原则、技术选型、分层架构、数据库规约 | `.sunshine/spec/system.md` |
| 前端：组件、样式、状态管理、页面、交互约束 | `.sunshine/spec/frontend.md` |
| 后端：接口、数据模型、错误处理、Token、并发 | `.sunshine/spec/backend.md` |
| 某层内容太多、一份文件装不下 | `.sunshine/spec/<分层>/` 下按主题拆文件，每份配自己的 `## 索引` |

一份文档混讲前后端时，按内容拆到对应的文件，不要整份塞进一个文件。

## 步骤 3：按 spec 的样子写

- 每份文件保留原意，只做三件事：分节（每节一个 `##` 标题）、去重（同一条规则只留一处）、补索引（见步骤 4）。
- 接口、字段、枚举、状态值、错误码要原样保留，一个字不改；不确定的地方标出来，不要自己定。
- 原文档的例子、反例、警告要保留，它们是规范最有用的部分。

## 步骤 4：配好索引

每份写完的 spec 文件，头上加 `## 索引` 一节，格式照模板：

```markdown
## 索引

索引是导航，不是替代：先读索引定位，再按需读正文；拿不准就读正文。

| 内容 | 位置 |
| --- | --- |
| 接口总览（健康检查、商品、订单） | `## 接口总览` |
| 数据模型（商品、订单、优惠券） | `## 数据模型` |
```

- 索引只列 `##` 大节，不列 `###` 子节。
- 每行一节：内容列写“标题（这一节讲什么）”，位置列写“`## 标题`”。
- 写完后跑一遍 `sunshine spec index` 核对：它会按标题重排索引、补上漏的节、删掉没了的节，旧描述保留。

## 步骤 5：对账，缺失的列出来

写完后给用户一份对账单：

- 整理进了哪些文件、每份有几节。
- 原文档里哪些内容没地方放（不知道归哪、或与现有规范冲突）。
- 哪些地方是文档里没写、需要用户补的（缺失的接口字段、没定的状态值、没说的错误码）。

缺失的部分不要编，等用户补了再进 spec。

---

## 质量检查清单

整理完之前：

- [ ] 原文档的意思有没有走样？接口、字段、枚举、错误码是否原样保留？
- [ ] 每份 spec 文件头上有 `## 索引` 一节吗？索引列出的节和正文对得上吗？
- [ ] 跑过 `sunshine spec index` 核对了吗？
- [ ] 有没有发明原文档没有的内容？缺失的部分列出来了吗？
- [ ] 有没有覆盖 `.sunshine/spec/` 里已填好的内容？
